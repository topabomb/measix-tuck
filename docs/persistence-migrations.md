# 持久化版本与迁移

本文描述已实现的正式 Go v1 → v2 迁移及后续维护约定。实现入口为 [migrations.go](../internal/tuck/migrations.go)，结构识别在 [storage_schema.go](../internal/tuck/storage_schema.go)，离线数据检查在 [persistence_check.go](../internal/tuck/persistence_check.go)。正常启动只接受当前版本或初始化空库，不在启动过程中升级已有数据。

## 所有权与版本

| 持久内容 | 版本及事实来源 | 迁移与保留规则 |
| --- | --- | --- |
| 唯一配置 `tuck.config.json` | 顶层 `schemaVersion=2`，独立于数据库和程序版本 | 配置 owner 校验后原子替换；保留密码哈希、credentialKey、身份、路径、用户参数及合法原生扩展 |
| Tuck `tuck.db` | `application_id=0x5455434b`、`user_version=2`，并核对完整实际 DDL | 编号 SQL 和必要的数据变换在一个事务内提交；不根据表名或版本数字猜来源 |
| tasks / messages / events 的 JSON | 由数据库版本统一管理；不在每个 DTO 再加一套版本 | 结构或语义变更必须写数据库迁移；原生事件正文属于外部公开合同，保留原值 |
| `task_deliveries.files_json` 与 `deliveries/snapshots/<task>/<delivery>/files/<file>` | 当前文件布局 v1；其解释由数据库版本管理 | 当前迁移不搬移或重写文件；保留交付 ID、版本、摘要、路径、大小和 SHA256 |
| `platform_session` | `format_version=2` 独立标识平台密文格式；解密后的绑定形状由该格式管理 | 保留安装身份、绑定、凭据、快照、pendingRefresh 幂等键与 applied 回执；密钥丢失时拒绝，绝不生成新密钥覆盖旧身份 |
| `web_sessions` / `login_limits` | 数据库版本 | 迁移保留令牌哈希、CSRF、身份、到期和限流事实；之后仍按正常认证规则过期或撤销。设置解锁仅在内存中 |
| `mcp_catalog` | 数据库版本；内容必须是最多 4 MiB 的工具数组 | 只表示最近成功验证。v1 中非数组或超出读取上限的缓存可以丢弃重建，不伪造在线、不重做授权 |
| workspaceRoot、任务指定目录、uploads | 用户文件；上传登记及任务的实际目录由数据库版本管理 | 文件可被用户独立修改或删除，不因迁移重建、重命名或重放工具；历史任务实际目录不能用当前助手默认目录替换 |
| `native/`、`native-config/` | 官方 Docker Agent 的不透明资产 | 只在停止对应引擎后做完整文件备份；Tuck 不识别、查询或迁移原生 SQLite schema |
| `runtime/agent.yaml`、`engines/<version>/` | 配置和官方发行清单可重建的输入/程序 | YAML 不作为用户配置迁移；引擎程序按官方版本、摘要和公开接口验证，不能只因缓存存在就判定成功 |
| 浏览器外观、面板宽度及返回位置 | 前端 `tuck.appearance.v1`、标量偏好、sessionStorage | 不属于后端权威数据；不复制到业务库，不参与后端迁移 |

产品版本、配置版本、Tuck 数据库版本、平台密文格式、上游 Snapshot v4/v5、Workspace Projection 版本和官方引擎版本分别演进。上游版本、快照内容、哈希和 ETag 原样保留，不能为适配本机版本重签或重写。

资源所有权也约束应用时机：server、storage、auth、credentialKey 和引擎 mode/version/binary/url 的外部编辑需要停服后核对并重启，不能由运行配置页把整个文件标为已应用。独立官方引擎升级可以切换其已验证版本。当前不提供数据目录自动搬迁或密钥轮换；改路径、改密钥和修改格式版本数字都不能替代迁移或恢复。

## 当前迁移

配置 1 → 2 保留所有设置，只提升版本并要求有效的 32 字节 `security.credentialKey`。v1 初始化生成的原密钥继续使用；缺失密钥的旧文件需先从匹配备份恢复，不自动补随机值。新建安装仍由 `tuck init` 生成独立密钥。所有写入在保存前限制为自身可读取的 4 MiB，包括格式化后的配置和加密前的平台状态。

完整校验也覆盖本机工具数量、引擎路径类型，以及平台模型参数/工具选择的对象类型。错误的数组、null 或标量不能静默转成空对象，尤其不能因此把明确的工具选择解释为默认全部授权范围。格式正确的值原样保留；不符合合同的旧文件先明确修正，再执行迁移。

数据库 1 → 2 使用 [001.sql](../internal/tuck/contract/storage/001.sql) 和 [002.sql](../internal/tuck/contract/storage/002.sql)。v1 是已发布基线，v2 增加平台密文 `format_version`，将 AES-GCM AAD 从固定字符串升级为包含格式版本与 installation_id 的认证内容，并将 MCP 缓存约束收紧为可读取的数组。原平台明文字节解密校验后直接重新加密，既不转换 Snapshot，也不刷新凭据或访问平台。没有平台行时不创建虚构绑定。

任务、消息和单事件沿用 128 MiB 读取上限，MCP 目录沿用 4 MiB 上限，写入也使用同一上限。超限或序列化失败返回明确错误，不写入重启后无法读取的记录；任务/消息/事件的联合发布整体回滚，保留旧消息、任务和游标。Go 的 nil 工具切片规范化为空数组，仍与“没有缓存记录”区分。

升级保留任务 ID、nativeSessionId、消息 position/revision、事件 seq 及 AUTOINCREMENT 高水位、轮次统计、交付版本、Web 会话和登录限流。迁移不广播执行事件、不重新执行队列或工具、不触发交付保留裁剪。数据库提交后的普通启动恢复仍按现有规则收束中断任务和暂停队列。

封存 Node demo 即使也有 `user_version=2`，其 application_id、DDL 和配置来源仍不同，不属于此链。未知、未来版本、被改动的已发布 DDL 和封存结构均明确拒绝；不会清空数据、猜测导入或自动降级。历史行为对比不等于历史存储格式兼容。

## 执行与中断恢复

先停止使用该配置或数据目录的 Tuck 服务及对应引擎，再用目标版本程序执行。程序对配置和数据目录使用操作系统排他锁，覆盖服务与维护命令，进程崩溃自动释放。锁文件保留原 inode，不手工删除；旧版 Tuck 和外部 SQLite 工具不遵守此锁，因此停服仍是维护前提。外接引擎由宿主管理，必须由其 owner 停止后才能复制原生资产。

```text
tuck migrate --check --config /path/to/tuck.config.json
tuck migrate --backup /backup/tuck-before-v2 --config /path/to/tuck.config.json
tuck migrate --check --config /path/to/tuck.config.json
tuck serve --config /path/to/tuck.config.json
```

Windows 使用 `tuck.exe` 和实际 Windows 路径。`--check` 打开只读业务库，核对配置、DDL、quick_check、foreign_key_check、平台解密与安装身份、JSON/类型列一致性，以及所有已提交交付文件的类型、大小和 SHA256。检查文件流式读取，不把历史或文件整体载入内存。它不修复内容，也不清理孤儿；锁文件和 SQLite 必需的协调侧文件不属于业务变更。大量交付文件会增加离线检查时间。

`--backup` 必须指定一个尚不存在、父目录已存在且位于 dataDir 之外的目录。先完成同样检查，再保存原配置字节、`VACUUM INTO` 一致 Tuck 库和 `manifest.json`；清单标明范围、源路径、源/目标版本和 SHA256。备份文件以 0600、目录以 0700 创建（Windows 仍受宿主 ACL 约束）。备份库通过结构与完整性检查，文件和目录同步后才开始迁移。备份失败不变更源格式；未生成完整 manifest 的目录视为不完整备份，不能覆盖复用。

备份范围是 `migration-inputs`，不是完整部署备份：本次迁移只变更配置和 Tuck 库，工作文件、快照及原生资产不变。发布前仍需另外做下文规定的完整冷备份。已是当前版本时重复执行为无写入操作，不创建多余备份；不存在或真正空白的库留到首次启动初始化。

数据库 DDL、平台密文和 user_version 同事务提交，失败整体回滚。之后再次比较配置原始字节，原子保存配置。配置与 SQLite 不能联合原子提交：断电或写配置失败可能留下“配置 v1 + 数据库 v2”。这是一种可识别的中间状态；保留第一次备份，重新检查，再用另一个新备份目录续迁，只完成余下配置。反向组合“配置 v2 + 数据库 v1”也可检查并仅迁移数据库。不得只手改版本数字绕过检查。

## 完整备份与回退

发布前冷备份必须包含原配置及 credentialKey、完整 dataDir、workspaceRoot，以及配置中和历史任务实际引用的所有外部工作目录。包含主库/WAL/SHM、交付快照、附件、官方引擎不透明资产及必要程序版本；先停止服务和引擎，再复制并验证。运行中的 `VACUUM INTO` 只证明 Tuck 库一致，不能证明文件及原生上下文与它同时一致。

若迁移完成后尚未启动任何写入者，本次变更输入备份可恢复配置与 Tuck 库；停服时移走当前库及其 WAL/SHM，恢复备份的库到清单中的源路径，并恢复匹配的原配置。备份库是独立一致快照，不混用现有 WAL/SHM。若迁移前没有库，按清单和完整冷备份恢复该不存在状态，不留下新库给旧程序使用。

发生持久化格式变化且新程序已开始运行时，回退须恢复与旧程序匹配的整套冷备份，不能只换二进制、配置或一个库文件；恢复会撤销备份之后的写入，须先保留当前资产并确认数据取舍。未改变存储格式的程序替换按其已验证兼容范围回退，不把旧备份覆盖到最新数据。当前不提供自动降级 SQL。恢复后核对 quick_check、foreign_key_check、任务/消息数量、事件游标高水位、消息修订、安装身份、交付版本和文件 SHA256，再通过官方公开 API 检查原生会话。新旧程序的验收分别记录，健康检查不能替代历史、交付下载、模型或 DAV 验收。

## 后续修改约定

1. 每次修改先列明 owner、已发布源版本、目标版本、支持路径、保留身份和失败边界。仅新增展示字段且不改变旧数据解释时无需机械地提升格式版本；字段含义、必填条件、加密规则、SQL 或文件解释变化必须定义迁移。
2. 已发布编号 SQL 不改写、不补 `IF NOT EXISTS` 掩盖漂移；增加下一个步骤并同步最新版本、结构识别、初始化链和数据变换。配置也必须追加明确的版本步骤，不能把任意旧数字直接改成当前数字。
3. JSON 由数据库版本管理，密文由平台格式管理；不能散落到各 HTTP handler 自动“修复”。所有权不变时优先复用 config、Store、Platform 和交付 owner，不添加迁移后台、轮询、第二业务库或常驻兼容分支。
4. 未来文件布局变更须先复制到新布局、校验并同步，再事务切换数据库引用；旧文件在确认引用和回退边界后清理。不能原地搬走仍被已提交记录引用的文件。当前迁移没有文件布局变换。
5. 覆盖空安装、每个支持的旧版和混合中间状态、重复执行、未知/未来格式、错误密钥、备份/DDL/配置保存失败、游标与交付保留、恢复后读取和进程占用。用真实发布基线夹具保留事实，不能只测试新建空库。

回归入口见 [migrations_test.go](../internal/tuck/migrations_test.go) 和 [验证指南](verification.md)。v1 配置夹具使用冻结的[无凭据发布模板](../internal/tuck/testdata/config-v1.json)，业务库由冻结的 001.sql 构造；不从未来默认值反推旧配置。本机测试与冷备份恢复不能证明真实断电、坏盘或尚未部署的外部服务行为。
