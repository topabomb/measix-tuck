# Docker Agent 临时补丁

默认使用官方 Docker Agent。上游缺陷已复现、且尚无可用的官方修复版本时，必须先取得用户明确同意，才可制作和应用最小临时补丁；上游正式版本包含完整修复后，验证并切回官方新版，撤除对应补丁。不维护长期定制引擎。

## 约定

- **禁止自行决定打补丁。** 即使问题已由官方 issue、PR 或维护者确认，也不等于获得修改引擎的授权。先向用户说明问题、官方修复状态、最小修改范围、验证方式和风险，询问并取得明确同意后，才能制作、修改、编译或应用补丁；本地试打也受此约束。可以先只读排查，并用未修改的官方版本复现，但不能把排查或复现授权解释为打补丁授权。
- 已有明确授权在原定范围内继续有效，无需重复询问；更换问题、基线或扩大修改范围须重新取得同意。更新生产还必须有相应的部署授权，不能把本地补丁验证的同意当作生产发布许可。
- 先核对实际使用版本的官方配置、公开接口及相关 issue、PR、release。已有可用官方修复时优先验证升级；本地补丁应关联上游问题并持续跟进。向上游发言遵守当前任务的授权。
- 补丁只修复已确认的引擎缺陷，包含必要回归，不夹带产品功能、重构或无关优化。Tuck 仍通过公开配置、CLI、HTTP/SSE 使用引擎，不导入内部运行时包，不读取或修改原生 SQLite，不在网关或工作台另造执行、重试、审批和恢复循环。
- 本目录只维护这一份说明和当前需要的 `.patch` 文件，命名为 `<官方版本>-<问题简称>.patch`。每个补丁在本文记录上游关联、状态、适用范围、冻结基线、构建及摘要、验收结论和撤除条件；暂不增加逐补丁目录、独立构建清单或管理框架。
- 修改必须在干净的独立检出中进行，冻结官方 tag 和 commit，应用前执行 `git apply --check`。换基线、改补丁或重新构建都要重新记录摘要及验收，不能模糊套用、静默跳过冲突或复用旧结论。
- 源码、测试与依赖改动必须可审查。程序使用明确的补丁版本标识，记录 Go 版本、目标平台、构建参数、补丁及程序 SHA256；不冒充官方程序，不覆盖官方发行包或修改其校验值。
- 凭据、生产地址、会话、数据库、程序、日志及详细运维回执不进入本目录。私密维护材料放在已忽略的 `.production/`；验收后清理可重建临时产物，保留必要记录和有效回退资产。

## 验证、发布与回退

1. 用官方基线复现，再证明补丁消除原故障。回归覆盖正常、失败和恢复边界；涉及协议或多模态时检查实际序列化内容、调用来源及真实模型可见性，不能只看 HTTP 200。区分合成测试、公开旧历史副本与生产实际执行，不为验证而重放旧工具。
2. 执行相关包回归、构建及适当的静态检查，扩展范围与影响相称。环境失败或未验证分支如实记录，不把拆分重验表述成单次全量通过。
3. 在既有任务授权范围内，按[部署与维护规则](../../docs/deployment.md#更新回退和数据)确认活动任务及队列，协调维护，停止服务和托管引擎，完整冷备份配置、数据及实际工作目录。涉及持久化解释变化时，先遵守[迁移约定](../../docs/persistence-migrations.md)，不靠补丁隐式迁移内部数据。
4. 托管实例通过已有 `engine.binary` 选择独立持久路径中的补丁程序，保留官方程序和发行校验；外接实例由其宿主管理。不得只覆盖容器可写层。记录实际配置差异及运行中程序摘要，再验证健康、公开会话、业务数据、交付文件和相关权限。
5. 失败时按已验证的数据兼容范围回退程序与配置；原生资产需要匹配时按既有备份规则恢复。已发生新业务写入后，不得用旧备份覆盖最新数据。详细回退步骤随补丁实际影响记录，不查询或手工修补原生库。

## 跟进上游与撤除

沿用已有 issue 跟进任务，不为每次检查另建自动化。检查维护者意见、关联 PR、修复提交和正式 release/tag 的包含关系；issue 关闭、PR 合并或出现新版本号都不能单独证明修复已可用。

正式版本包含修复后，用官方程序重跑同等缺陷回归、相关业务语义及旧会话恢复验证。上游可以采用不同实现；判断依据是原故障和业务语义是否正确，不要求逐行复刻本地补丁。部分修复或通过丢失图片等信息规避错误，不满足撤除条件。

验证通过后，按当前任务授权和正常官方升级流程切回官方新版，移除临时 `engine.binary` 选择；需要调整嵌入发行基线时按常规发行流程处理。生产验收通过后删除已替代的 `.patch`、不再使用的定制程序和专用适配，不保留两套运行逻辑。本文只留简短撤除记录：替代的官方版本/提交、验收与切换日期；详细历史由 Git 和必要的私密回执保留。备份按现有保留规则清理。

定时任务只读检查、报告实质变化；它不自动修改代码或生产。发现正式修复后应推动验证和切回，不以维持本地补丁为默认选择。

2026-10-18 已向 #4629 [补充实际引擎识图、旧历史回放、生产恢复及显式缓存分支的集成建议](https://github.com/docker/docker-agent/issues/4629#issuecomment-6251482700)，并注明当前补丁不直接适用于 main，接受满足同等行为的上游实现。此为已发布证据，跟进任务不重复通知其创建，继续关注维护者回复与后续修复。

### 修改与适用范围

官方 v1.150.0 在每个工具结果后立即追加 user 图片附件，可能形成 `tool → user(image) → tool`，打断尚未结束的并行工具返回批次。补丁暂存生成的附件，在连续有效工具结果结束或输入结束时输出；先跳过已有规则过滤的空 assistant。工具完成顺序不变，附件仍为原生图片/文档内容块，载荷和 detail 不变，标签附带 `tool_call_id` 保留来源。不补造真正缺失的工具返回。

只修改 `pkg/model/provider/oaistream/messages.go`（+12/-2）及 `messages_test.go`（+117）。补丁见 [v1.150.0-tool-image-order.patch](v1.150.0-tool-image-order.patch)。

当前 Tuck 的 `tuck-chat` 及哈希模型键走完整消息列表转换，已实际验证。DMR 复用转换器且包回归通过，未做 DMR 真实模型验收。官方 OpenAI 显式 prompt-cache 分支逐条调用转换器，无法跨调用暂存附件，不在这个最小补丁覆盖范围。Responses、Anthropic、Gemini、Bedrock 的原生转换未改，只有包回归，没有新增真实模型验收。不能把此补丁宣称为所有引擎配置的完整修复。
